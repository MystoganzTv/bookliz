## P0 — Pérdida de datos

### ~~P0-A~~ · ARREGLADO — Un fallo de red al arrancar sobrescribía la biblioteca real con datos mock

> **Cerrado el 10/08/2026.** `load()` ahora aísla cada ruta en su propio `try`, el
> fallback local se ejecuta siempre, y `RepositoryStatus.localReadFailed`
> distingue "no hay nada" de "no pude leer". Si la lectura local falla,
> `persistBlockedRef` bloquea toda escritura hasta que un `load()` posterior
> tenga éxito. 6 tests de regresión en `src/__tests__/repositoryLoadFallback.test.ts`.
> Descripción original abajo.

**Archivos:** `src/data/booklizRepository.ts:150-157`, `src/data/BooklizContext.tsx:738-806`

`load()` envuelve las tres rutas (Supabase → remoto → AsyncStorage) en un solo
`try`. Si la primera falla, el `catch` devuelve `null` **sin llegar nunca a leer
AsyncStorage**:

```ts
} catch (error) {
  this.status = { ...this.status, syncState: "error", ... };
  return null;   // ← el snapshot local nunca se intentó
}
```

`hydrate()` interpreta ese `null` como "instalación nueva", sale por el `return`
temprano y deja el estado en los seeds de `mockData.ts`. El `finally` marca
`hydrated = true`, lo que dispara el efecto de persistencia local a los 600 ms:

```ts
useEffect(() => {
  if (!hydrated) return;
  const timer = setTimeout(() => void persistNow.current(true), LOCAL_PERSIST_DEBOUNCE_MS);
}, [authors, books, hydrated, ...]);
```

…y escribe Le Guin, Sanderson y compañía encima de `booklio:v2`. La biblioteca
del usuario desaparece del disco.

Verificado con un test temporal: con un snapshot válido en AsyncStorage y `fetch`
lanzando, `load()` devuelve `null` y `syncState === "error"`, mientras el snapshot
sigue intacto en disco.

**Arreglo:** separar los `try`. El fallback local debe ejecutarse siempre que el
remoto falle, y `hydrate()` debe distinguir "no hay nada" de "no pude leer" —
ante error, no marcar `hydrated` o no persistir.

### ~~P0-B~~ · ARREGLADO — La nube siempre ganaba y se perdían las ediciones offline

> **Cerrado el 10/08/2026.** Resolución por **marcador de sincronización**, no por
> comparación de fechas. `LOCAL_SYNC_MARKER_KEY` guarda el `updatedAt` del último
> snapshot que este dispositivo subió con éxito; el local va por delante cuando su
> `updatedAt` difiere del marcador. Los dos valores los escribe **el mismo reloj**,
> así que la comparación nunca cruza relojes — un móvil con la hora mal no puede
> ganar ni perder todos los conflictos.
>
> - Local por delante → gana el local, se marca `localAheadOfRemote` y el provider
>   lo sube nada más hidratar (sin esperar a que el usuario edite algo).
> - Local es espejo fiel del último push → gana la nube y el marcador avanza.
> - Sin marcador (reinstalación, restauración de backup) → gana la nube: sin
>   prueba de que el local va por delante, no se destruye la copia remota.
> - El marcador solo avanza si la subida **ocurrió de verdad**: `saveSupabase`
>   devuelve `false` si no hay sesión, y un `save({ localOnly })` no lo mueve.
>
> **Sobre los dos dispositivos:** la resolución a nivel de snapshot siempre
> descarta un lado, y con dos dispositivos ese lado puede tener trabajo real. Por
> eso el snapshot perdedor se aparca en `CONFLICT_BACKUP_KEY` con su fecha, y
> `RepositoryStatus.conflictBackupAt` lo expone. Nada se pierde en silencio, pero
> **sigue habiendo un descarte** — ver P0-B2. 10 tests de regresión.
> Descripción original abajo.

**Archivo:** `src/data/booklizRepository.ts:88-102`

```ts
const supabaseSnapshot = await this.loadSupabase();
if (supabaseSnapshot) {
  await this.storage.setItem(this.storageKey, JSON.stringify(supabaseSnapshot));
  return supabaseSnapshot;
}
```

No hay comparación de `updatedAt`. Escenario: el usuario edita sin cobertura
(local queda al día, nube no), cierra la app, la reabre con red → el snapshot de
la nube, más antiguo, pisa el local. Todo lo hecho offline se pierde.

El dato para arreglarlo ya existe: las migraciones tienen trigger
`booklio_set_updated_at` en las seis tablas, así que `profileRow.updated_at` es
hora real de servidor.

**Arreglo:** leer también el snapshot local y quedarse con el `updatedAt` mayor.
Si el local gana, subirlo en vez de descartarlo.

### P0-B2 · ABIERTO — Con dos dispositivos, la resolución por snapshot sigue descartando un lado

Consecuencia directa de usar Bookliz en más de un dispositivo. Si editas en el
móvil **y** en el iPad antes de que ninguno sincronice, ambos lados tienen
trabajo legítimo y P0-B solo sabe elegir uno entero. El perdedor queda en
`CONFLICT_BACKUP_KEY` — recuperable, pero no aplicado.

El arreglo real es **fusión por registro**: unir libros, sesiones y reseñas por
`id` quedándose con la versión más reciente de cada uno. Lo que hace falta:

1. Un `updatedAt` **por registro** en el snapshot local. Hoy solo existe a nivel
   de snapshot; en Supabase sí está por fila (trigger `booklio_set_updated_at`),
   así que el esquema remoto ya sirve.
2. **Tombstones** para los borrados. Sin ellos, unir por `id` resucita lo que
   borraste en el otro dispositivo: no se puede distinguir "borrado aquí" de
   "añadido allí".
3. Migración del snapshot local a v3, rellenando `updatedAt` por registro con la
   fecha del snapshot en la primera carga.

Mientras tanto, el riesgo está acotado y es visible: nada se pierde en silencio.

## P1 — Bugs reales

### ~~P1-A~~ · ARREGLADO — `expo-haptics@56.0.3` en un proyecto SDK 54

> **Cerrado el 10/08/2026.** `npx expo install --fix` →
> `expo-haptics` 56.0.3 → 15.0.8, `jest-expo` 56.0.4 → 54.0.17,
> `expo` ~54.0.0 → ~54.0.36. `expo install --check` limpio, typecheck limpio,
> 371 tests en verde. El wrapper `src/utils/haptics.ts` solo usa
> `impactAsync` / `notificationAsync` y sus enums, estables en la 15.x, así que
> no hizo falta tocar código. Descripción original abajo.

`npx expo install --check`:

```
expo-haptics@56.0.3 - expected version: ~15.0.8
jest-expo@56.0.4    - expected version: ~54.0.17
expo@54.0.35        - expected version: ~54.0.36
```

Un salto de major del 15 al 56 no es un desfase menor: ese paquete apunta a un
SDK futuro. Riesgo de fallo de build nativo o crash en runtime al llamar a
háptica. `legacy-peer-deps=true` en `.npmrc` es lo que permitió instalarlo sin
avisar.

**Arreglo:** `npx expo install --fix`.

### P1-B · IDs generados solo con `Date.now()`

**Archivo:** `src/data/BooklizContext.tsx:485, 1405, 1424`

```ts
id: `rs-${Date.now()}`      // sesión de lectura
id: `rev-${Date.now()}`     // reseña
id: `list-${Date.now()}`    // lista
```

Sin discriminante. Dos registros creados en el mismo milisegundo comparten ID, y
como el sync usa `upsert(..., { onConflict: "id" })`, uno se traga al otro en
silencio. También colisionan como `key` de React.

Los libros y autores sí llevan slug (`b-${slug}-${Date.now()}`), así que el
riesgo real está en sesiones/reseñas/listas — sobre todo si algún día hay
importación en lote.

**Arreglo:** añadir sufijo aleatorio, como ya hace `offlineQueue.ts:74`.

### P1-C · La cola offline crece sin techo y nunca cuenta reintentos

**Archivos:** `src/utils/offlineQueue.ts`, `src/data/BooklizContext.tsx:895-905`

Cada sync remoto fallido mete un marcador nuevo:

```ts
void enqueue("upsert_profile", { reason: "full_sync_needed", timestamp: Date.now() });
```

Con el debounce remoto en 10 s, una sesión offline de una hora deja ~360 entradas
duplicadas en AsyncStorage. Y `markRetried()` está exportada pero **no la llama
nadie**: el flush hace `clearQueue()` al acertar y `console.warn` al fallar, así
que `MAX_RETRIES = 5` nunca se aplica y un fallo permanente se reintenta cada vez
que la app vuelve a foreground.

**Arreglo:** antes de encolar, comprobar si ya hay un marcador `full_sync_needed`
pendiente; y llamar a `markRetried` en el `catch` del flush.

### P1-D · `isOnline()` devuelve `false` cuando el estado es indeterminado

**Archivo:** `src/utils/offlineQueue.ts:118-121`

```ts
return state.isInternetReachable === true && state.isConnected === true;
```

`isInternetReachable` puede llegar `undefined` en varias plataformas. Con ello el
flush de la cola no se ejecuta nunca aunque haya red perfectamente utilizable.

**Arreglo:** `state.isConnected === true && state.isInternetReachable !== false`.

### P1-E · `pruneOrphans` se rompe en silencio con bibliotecas grandes

**Archivo:** `src/data/booklizRepository.ts:377-388`

```ts
await supabase.from(table).delete().eq("user_id", userId).not("id", "in", `(${keepIds.join(",")})`);
```

La lista de IDs viaja en la query string. Con unos cientos de libros
(`b-<slug>-<ts>` ≈ 30-40 caracteres cada uno) se superan los límites de URL y
PostgREST responde 414. Además el `catch {}` solo atrapa excepciones —
supabase-js devuelve los errores en `{ error }`, no los lanza — así que el fallo
es doblemente invisible: filas huérfanas que nunca se limpian.

**Arreglo:** trocear `keepIds` en lotes (~200) y comprobar `{ error }`, aunque
sea solo para loguear.

### P1-F · Google Sign-In iOS: placeholders sin rellenar *(ya en AUDIT.md como P0-1, sigue abierto)*

`app.json`:

```json
"iosUrlScheme": "com.googleusercontent.apps.TU_REVERSED_IOS_CLIENT_ID"
"iosClientId": "TU_IOS_CLIENT_ID.apps.googleusercontent.com"
```

Nota añadida: `getGoogleAuthConfig()` hace `config.iosClientId ?? config.webClientId`,
pero el placeholder es un string truthy, así que el fallback **no se activa**. En
iOS se envía un client ID inválido en lugar de degradar al web. Poner la clave o
borrar la línea; dejarla es peor que no tenerla.
